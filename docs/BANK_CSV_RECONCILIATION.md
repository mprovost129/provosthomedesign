# Live FreshBooks payout and bank CSV evidence

This owner-only workspace records reviewed matches between original payout exports and bank CSV deposits. It creates no invoice, payment, fee, revenue or ledger entry and makes no provider API requests. Live and sandbox sources use different models and routes. FreshBooks continues production billing.

## Sources

Open Dashboard → Billing → Review bank deposits, or Invoices → Bank deposits. Select the payout initiation month. In FreshBooks Settings → Online Payments → Visit Stripe Dashboard, verify the FreshBooks-linked account in live mode. Export the whole month’s payouts plus one extra day at each end, with all statuses and **All columns (22)**. For September, use August 31–October 1. Padding protects UTC/Eastern boundaries; normalization retains only payouts initiated in the selected Eastern month. Source account identity and coverage require uploader attestation: the CSV has no account ID. This is a saved source export, not an automatic feed.

The original October 30, 2026 export exposes payout ID, amount in currency units, created/arrival dates, currency, Livemode, destination last four digits, status and bank trace ID. Normalization retains only those necessary facts, method/type and trace status, plus file fingerprint, selected FreshBooks business, month, actor and time. Bank names, full destination IDs and payment descriptions are discarded. Payout IDs must be unique and live mode explicit. Meaningful sub-cent amounts are rejected; no rates or fees are estimated. UTC created timestamps are converted to Eastern time for month selection. UTC midnight arrival dates remain calendar arrival dates; converting them to Eastern would shift them a day earlier incorrectly.

FreshBooks documents its payout status and timing separately from bank posting: https://support.freshbooks.com/hc/en-us/articles/47262906310669-How-do-I-manage-my-payouts-with-FreshBooks-Payments . A source “Paid” status is not itself bank-statement confirmation.

## Bank CSV workflow

1. Upload a bank CSV of up to 1 MB, with a bank label, last four account digits, explicit currency, encoding and header row. The browser then displays source columns and five sample rows.
2. Choose date and description columns, US or ISO date format, and either a signed amount column or separate credit/debit columns. Optional reference, unique bank transaction ID and currency columns improve identification. No financial column is guessed. Empty split debit/credit cells mean no amount in that column; missing signed amounts are errors. Dot decimal amounts and correctly grouped thousands are accepted, with exact cents throughout.
3. Preview the positive deposits and excluded row counts. The review window includes the payout month plus adjacent-month spillover for transfers arriving later. Withdrawals and zero rows are counted but not persisted as transactions. Dates after today are not posted deposit evidence. Repeated bank identities within a file are retained and blocked from confirmation.
4. Confirm the statement account/currency/mapping, then save normalized positive-deposit evidence. Review each payout separately. Suggestions require exact amount, currency, destination last-four match and a deposit date from initiation through 31 days after expected arrival. They are not confirmations. An exact payout/trace reference is highlighted; otherwise a substantive owner review note is required. The owner must attest to the individual match in either case.

The original bank CSV is handled in memory and returned as a compressed signed preview payload in the authenticated response. It is not retained in a file, database batch or server session. Payloads expire after 30 minutes and are bound to owner, business, account and stage, with strict size limits. Preview responses are private/no-store/noindex. No full bank account number or running balance is persisted after saving. Only mapped positive-deposit facts, original row numbers, selected mapping, file fingerprint and provenance are retained. A bank CSV containing additional currencies must map that column or attest the account currency; no exchange conversion is performed.

## Matching, duplicates and corrections

Payouts are cash transfers after payment processing. Compare their amount directly with bank deposits. Do not subtract payment fees a second time or add payouts to revenue. All totals remain separated by currency. Confirmed totals include only current, intact, owner-reviewed evidence; missing and changed sources require review. This does not establish complete monthly income, bank opening/closing balances, withdrawal reconciliation or absence of later reversals.

Exact reimports reuse batches. Replaying an older payout file cannot restore superseded head facts. New complete payout exports preserve previous source batches, update heads and flag previously listed payouts missing from the same month. Changed payout economics/status or excluded/corrupt statement evidence invalidates confirmation projections rather than rewriting an old match.

Active matches are unique per payout and bank identity across CSV imports. When available, stable bank transaction IDs identify deposits across files. Otherwise an exact date/amount/reference/description fingerprint is used. Identical-date/amount deposits cannot be counted twice through different descriptions unless distinct bank IDs establish separate entries. Conflicting facts for the same bank ID require review. Matching amounts alone never trigger confirmation. The source CSV and reviewed identity remain the evidence; this is not an authenticated bank API.

Matches preserve both source snapshots and hashes. Undo requires a reason and retains the original reviewer, time and evidence. Incorrect bank imports can be excluded with an audit reason, retaining source history and causing dependent matches to need review. Correcting a bad import does not delete or alter bank/FreshBooks records. Shared queue locking, payout versions and database uniqueness prevent concurrent reuse. Only active superusers with existing workspace/change permissions may import or match; preview-mode writes and CSRF bypasses are rejected. Source text remains escaped in templates.
