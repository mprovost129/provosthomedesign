# Verified-email booking and initial consultations

Anyone with a valid verified-email session can book an available appointment. CRM membership, prior work, manual email enablement and consultation approval are not prerequisites. Legacy BookingAccess allow/deny records and ClientContact.booking_requires_approval flags remain as history but no longer restrict booking. Staff can cancel individual appointments with the existing appointment permission; project/document access rules are unchanged.

The public booking page accepts an email directly. The optional `/request-consultation/` form collects name, email, phone and project description with terms consent, CSRF, session-bound tokens, reCAPTCHA and IP/email rate limits. A consultation request does not reserve a slot or add work to the project queue.

An unverified consultation queues only a single-use email link, valid for 24 hours. Verification creates/reuses a CRM inquiry contact without granting staff, project or document access, records the existing `pending` state (displayed as “Ready to book”), notifies the owner and redirects the verified session to booking. Existing contact details are not overwritten. GET requests/email scanners do not consume tokens. Retries, including different form tokens and fresh sessions after verification, reuse the inquiry without duplicating contacts or notices. The original browser can request another link before verification.

Previously pending, approved or declined consultation records do not block a valid verified session. Visiting the old consultation URL while verified redirects directly to booking. No mass approval, historical data rewrite or bulk notification is required. The staff page lists verified inquiries without approve/decline or enable/disable controls. Stale staff action POSTs explain the new policy without changing access or sending decision emails.

The existing appointment flow still enforces identity and ownership, CAPTCHA/rate limits, Eastern time, 24-hour notice, business hours, meeting/buffer lengths, daily/client limits, idempotency and calendar conflict checks. Confirmation still waits for the calendar worker; verification alone does not create an appointment.

Apply migration `0040_consultation_ready_to_book` through the normal deployment. It changes only a display label; the persisted states and email uniqueness constraint remain compatible with old and new processes. Both revisions reuse and list verified `pending` inquiries during rollout. No `ready` rows are written and rollback performs no data conversion. A code rollback restores the old eligibility code; it must not silently revoke previously authorized visitors, alter legacy contact flags, or undo real appointments and notifications. Existing queued emails may contain the older approval wording, but their verification links now lead to booking. No real mail or calendar events are created by tests.

Availability page reads (including date-selection and booking POSTs) use the existing shared rate-limit cache: 30 requests per verified email and 60 per IP per minute. Excess requests receive HTTP 429 with `Retry-After: 60` and a retry link, without calling the calendar provider or reserving a slot. The verified session remains valid. Normal navigation and reservation/worker conflict checks use fresh calendar data; no cached availability is trusted to authorize a reservation.
